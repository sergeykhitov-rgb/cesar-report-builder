# Инструкция для программистов — постоянное хранение отчётов

Документ для разработчика, которому нужно довести платформу «Конструктор отчётов CESAR SATELLITE»
до продакшена: **сделать так, чтобы публичные ссылки на отчёты жили постоянно** (сейчас на бесплатном
хостинге данные могут теряться при перезапуске).

---

## 1. Что это за проект (архитектура)

Максимально простой стек — **Node.js без внешних зависимостей**. Ничего не собирается, `npm install`
не обязателен, запуск: `node server.js` (порт из `process.env.PORT`, по умолчанию 4600).

```
server.js                — HTTP-сервер: статика + API + публичные страницы
public/
  index.html, editor.js, editor.css   — редактор (форма + живой предпросмотр + кнопка «Сгенерировать»)
  report.html                          — публичная страница отчёта  (/r/<id>)
  report-render.js                     — общий рендер отчёта (один и тот же в редакторе и на публичной странице)
  theme.css                            — фирменная тема CESAR SATELLITE
  logo.png, logo-mark.png, hero-default.jpg
data/reports/<id>.json   — ХРАНИЛИЩЕ отчётов (именно это нужно заменить на постоянное)
```

**API (2 эндпоинта):**
- `POST /api/reports` — принимает JSON отчёта, генерирует `id`, сохраняет, возвращает `{ id }`.
- `GET  /api/reports/:id` — отдаёт JSON отчёта по `id`.
- `GET  /r/:id` — отдаёт `report.html`, который на клиенте запрашивает `/api/reports/:id` и рендерит.

**Модель данных отчёта** (то, что лежит в JSON):
```jsonc
{
  "id": "8f9b75a4ab4a",
  "createdAt": "2025-01-31T12:00:00.000Z",
  "title": "…", "subtitle": "…",
  "object": { "pin": "…", "owner": "…", "brand": "…", "model": "…", "plate": "…", "address": "…" },
  "heroPhoto": "/hero-default.jpg | data:image/jpeg;base64,…",
  "summary": { "alarms": "12", "incidents": "3" },
  "events": [ { "signal": "…", "date": "…", "time": "…", "address": "…", "photo": "data:…", "note": "…" } ],
  "manager": { "name": "…", "role": "…", "phone": "…", "email": "…", "photo": "data:…" }
}
```
> Фотографии сейчас хранятся **прямо в JSON в виде base64** (ужимаются в браузере перед отправкой).
> Это просто, но делает записи «тяжёлыми». В продакшене их лучше вынести в объектное хранилище (см. §3).

## 2. Задача: заменить файловое хранилище на базу данных

Менять нужно **всего одно место** — в `server.js` функции чтения/записи отчёта. Сейчас это:

```js
// СОЗДАНИЕ  (POST /api/reports)
fs.writeFile(path.join(DATA, data.id + '.json'), JSON.stringify(data), cb)

// ЧТЕНИЕ    (GET /api/reports/:id)
fs.readFile(path.join(DATA, id + '.json'), 'utf8', cb)
```

Замените их на запись/чтение из БД. Рекомендуется **PostgreSQL** (managed, с бэкапами).

**Схема (одна таблица):**
```sql
CREATE TABLE reports (
  id         TEXT PRIMARY KEY,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  data       JSONB NOT NULL
);
```

**Пример на `pg`** (единственная зависимость — добавить в `package.json`):
```js
const { Pool } = require('pg');
const pool = new Pool({ connectionString: process.env.DATABASE_URL, ssl: { rejectUnauthorized: false } });

// создать
await pool.query('INSERT INTO reports (id, data) VALUES ($1, $2)', [data.id, data]);

// прочитать
const { rows } = await pool.query('SELECT data FROM reports WHERE id = $1', [id]);
if (!rows.length) return sendJSON(res, 404, { error: 'not found' });
send(res, 200, JSON.stringify(rows[0].data), { 'Content-Type': 'application/json; charset=utf-8' });
```

Переменная окружения: `DATABASE_URL` (даёт хостинг БД). Больше в коде трогать ничего не нужно —
фронтенд, рендер и стили остаются как есть.

**Где взять бесплатный/дешёвый PostgreSQL:**
- **Render PostgreSQL** — если деплой уже на Render (в одном месте).
- **Supabase** — бесплатный Postgres + встроенное объектное хранилище для фото (см. §3).
- **Neon** — бесплатный Postgres, «спит» и просыпается сам.

## 3. (Рекомендуется) Вынести фотографии в объектное хранилище

Хранить base64-картинки в БД рабоче, но раздувает записи. Правильнее:
1. Принимать фото как файл (`multipart/form-data`) или загружать напрямую с клиента в бакет.
2. Класть в **S3-совместимое хранилище** (AWS S3, Cloudflare R2, Supabase Storage, Selectel).
3. В JSON отчёта хранить **URL** картинки, а не base64.

Это ускорит загрузку страниц и удешевит хранение. Точка изменений на клиенте — функция `fileToDataURL`
в `public/editor.js` (заменить на загрузку файла в бакет и сохранение URL).

## 4. Что ещё стоит добавить для продакшена

- **Авторизация операторов.** Сейчас редактор (`/`) открыт всем. Публичные отчёты (`/r/:id`) — намеренно
  открыты по ссылке, а вот доступ к созданию отчётов нужно закрыть логином (например, cookie-сессия или
  Basic Auth на `/` и `POST /api/reports`).
- **Бэкапы БД** (managed-хостинги делают автоматически).
- **Лимиты и валидация** на размер загрузки (в `server.js` уже есть `MAX_BODY` и функция `clean()`).
- **Срок жизни / удаление** отчётов, если нужно (добавить `DELETE /api/reports/:id` + кнопку).
- **Свой домен** (например, `reports.cesar-satellite.ru`) вместо адреса хостинга.

## 5. Ответ на вопрос «нужен ли фреймворк (React/Next)?»

**Коротко: сейчас — не нужен, и это осознанный выбор.**

Платформа намеренно сделана на «ванильном» коде без сборки. Плюсы для текущей задачи:
- деплой в одну команду `node server.js`, без билд-шага и node_modules;
- любой программист поддержит, ничего экзотического;
- страница отчёта грузится мгновенно, отлично печатается в PDF.

Это **не «голый/сырой» код**, а сознательно минималистичная архитектура: рендер отчёта вынесен в одну
переиспользуемую функцию (`report-render.js`), стили — в дизайн-систему (`theme.css`), API отделён от
представления. Для «сгенерировать красивый отчёт по ссылке» этого более чем достаточно.

**Когда имеет смысл перейти на React / Next.js:**
- появятся личные кабинеты операторов, роли и права;
- список/поиск/фильтры по всем отчётам, статистика, история версий;
- интеграции (CRM, выгрузки, уведомления);
- много интерактивных экранов, а не один редактор.

Тогда переход недорогой: функция `renderReport()` переносится в React-компонент почти 1:1, а хранение и API
уже описаны выше. У компании уже есть проекты на **Next.js** — логично мигрировать на тот же стек, если
проект будет расти. До этого момента усложнять не стоит.
